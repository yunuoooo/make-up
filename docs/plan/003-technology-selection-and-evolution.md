# 妆迹技术选型与运行时演进说明

Status: current architecture
Date: 2026-09-22

本文解释妆迹为什么从 OpenAI Agents SDK 方案转向 Pi Agent，记录各阶段的取舍、外部技术实践对决策的影响，以及当前瓶颈和下一步解决路径。

## 1. 先说结论

妆迹最终没有把 Agent 运行时绑定在 OpenAI Agents SDK 上，而是选择了项目内置的 Pi Agent：

- Pi 作为 `package.json` 依赖，随项目部署，不依赖开发者机器上的全局安装。
- Agent 的行为由仓库内的 `SKILL.md` 和 `references/` 驱动，运行时只负责加载技能、限制工具权限和转发事件。
- 小红书 MCP 通过 `.pi/extensions/xiaohongshu-mcp.ts` 接入，只暴露登录检查、搜索和详情读取三个只读工具。
- Pi 的 JSONL 事件流是运行事实来源，Langfuse 由 bridge 手工映射出运行、turn、模型调用、工具调用和淘宝卡片阶段。

这不是“OpenAI 模型不够好，所以换 Pi”，而是运行时边界和交付形态发生了变化：MVP 已经有一个能工作的 Pi 主链路，继续保留 Python OpenAI Agents 运行时只会形成两套并行实现，增加部署、调试和行为漂移成本。

可以把这次选型概括为：我们比较了四种路线，最后根据 Demo 的目标选择了 Pi Agent。

## 1.1 四种技术路线

### 路线一：直接调用模型 API，自己实现 Agent Loop

这是最底层的方案：应用自行解析模型的 tool call，执行工具，把工具结果放回上下文，再次调用模型，直到得到最终答案。

优点是控制力最高，可以完全控制重试、预算、状态机、错误处理和观测。缺点是需要自己实现 Agent Loop、工具协议、多轮上下文、流式输出、结构化结果校验、取消和 trace 等基础设施。它适合建设 Agent 基础设施，不适合当时快速验证美妆 Skill 的 Demo。

### 路线二：OpenAI Agents SDK

这是最初选择的方案。SDK 已经提供 Agent、Runner、工具调用循环、流式事件、session、handoff、guardrails、结构化输出和 tracing，能够快速搭建一个自主工具型 Agent。

它并不是不能做妆迹，也不是需要我们重新实现 Agent 内核；但应用层仍要负责 Agent instructions、工具 schema、MCP 生命周期、session、错误处理、重试策略、结构化输出、SSE 和业务观测。项目会逐渐从“验证美妆 Skill”转向“维护一套 Agent runtime”。

### 路线三：LangGraph 等显式工作流框架

这类方案把“澄清需求、搜索小红书、读取笔记、提取妆容特征、推荐产品、校验答案”建模成显式节点和状态图。

优点是流程可视化，状态、重试、恢复和人工审批都容易控制，适合长期运行的生产 workflow。缺点是需要先设计节点和状态结构，开发成本更高，也会限制早期探索阶段的灵活性。它更适合产品流程稳定后的生产化阶段。

### 路线四：Pi Agent

Pi 对我们来说更像一个已经封装好的 Agent Harness，而不只是模型 SDK。它把模型调用、Agent Loop、工具调用、Skill 加载、上下文读取、JSONL 事件流、provider 配置和 MCP 扩展放在运行时层。

我们主要关注 `SKILL.md`、`references/`、MCP 工具白名单和 bridge，而不是重新搭建一套 Agent 内核。这更符合 Demo 阶段的目标：验证妆容研究 Skill、小红书资料链路和产品推荐效果。

Pi 的代价也需要明确：结构化输出、JSONL 到 SSE/Langfuse 的映射、provider 差异、错误语义和部分预算控制仍需要项目自己维护；如果未来需要复杂的持久化 workflow，仍可能在 Pi 外增加 workflow controller。

### 1.2 选型对比

| 维度 | 自建 Agent Loop | OpenAI Agents SDK | LangGraph 类工作流 | Pi Agent |
| --- | --- | --- | --- | --- |
| 抽象层级 | 模型 API | Agent SDK | 显式状态图 | Agent Harness / Runtime |
| 主要关注 | 全部自己控制 | Agent、工具和 runtime 集成 | 节点、状态和流程恢复 | Skill、工具权限和业务效果 |
| Agent Loop | 自己实现 | SDK 提供 | 图节点驱动 | Pi 提供 |
| 灵活探索 | 最高 | 高 | 中 | 高 |
| 生产流程控制 | 自己建设 | 应用层建设 | 强 | 中，需要 bridge/controller |
| 部署复杂度 | 高 | 中，可能跨 runtime | 中到高 | 低，项目内自包含 |
| 主要代价 | 基础设施工作量大 | 应用层契约较多 | 初期设计和维护偏重 | 需要自己维护协议和观测 |
| 适合当前 Demo | 不适合 | 可以，但偏重 | 偏重 | 最匹配 |

因此最终选择 Pi，不是因为 OpenAI Agents SDK 不支持 ReAct，也不是因为 Pi 天然拥有更强的重试能力，而是因为 Pi 的抽象层更符合当前 Demo 的验证目标和项目的自包含部署要求。重试策略属于业务层控制：哪些错误可重试、最多几次、何时跳过、何时降级，四种路线都需要明确设计。

## 2. 技术演进时间线

### 2.1 产品先收窄为可验证的文本 MVP

最初的产品判断是：用户真正需要的不是美妆百科，而是“为了达到某个妆效，我该用什么产品”。因此 MVP 先做文字目标、小红书资料检索、妆容特点拆解、SKU 候选和可选的妆匣匹配，图片理解、长期记忆和交易闭环后置。这个范围决定了运行时必须支持工具调用和流式回答，但不需要一开始就建设复杂推荐模型。

依据：`docs/specs/001-mvp.md`。

### 2.2 第一版选择 OpenAI Agents SDK

2026-09-04 的实施计划把运行时设计为 Python `openai-agents` 自主 ReAct Agent。选择它的原因是：

- Agent、Runner、工具调用、流式事件是现成抽象，可以快速验证“模型自己决定检索顺序”的产品假设。
- 计划中的 guardrails、结构化输出、session、usage 和 tracing 正好对应妆迹的安全边界、答案契约和 Langfuse 需求。
- Python 生态便于先把小红书、淘宝、妆匣等领域工具拼起来，也方便做离线 eval。
- 当时的目标是少写固定 workflow，让 Agent 自己组合 `search_xhs_evidence`、妆容分析、妆匣匹配和淘宝检索。

这个方案的代价也很明确：Next.js 前端/API 之外再维护一个 Python FastAPI 运行时，需要跨语言传递 SSE、错误码、结构化答案、session 和 trace；部署物还要同时包含两套依赖和生命周期管理。SDK 的自动 tracing 对同进程调用很方便，但一旦模型和工具经过独立服务，真正的调用链仍需要自己的业务观测层。

### 2.3 中间阶段接入小红书 MCP

小红书不是普通数据库查询，而是依赖登录态和浏览器驱动的外部资料源。项目没有把上游 MCP 的所有能力直接交给 Agent，而是在业务边界内保留一个受控入口：

```text
Agent -> 只读的 XHS 入口 -> xiaohongshu-mcp -> 搜索/详情
```

这样做是因为上游还提供发布、评论、点赞、收藏和删除 cookies 等副作用工具。把整个 MCP server 直接挂到 Agent 上会扩大权限面，也会让上游工具名称成为产品契约。当前扩展只注册 `check_login_status`、`search_feeds`、`get_feed_detail`，并对详情超时过的笔记做本轮跳过记忆。

依据：`docs/specs/09-07-xhs-mcp-integration.md`、`.pi/extensions/xiaohongshu-mcp.ts`。

### 2.4 最终迁移到项目内 Pi Agent

2026-09-17 的两个提交完成了切换：

- `d4294f2 feat: run the agent on a project-local Pi runtime`
- `73156bb refactor: drop the Python OpenAI Agents runtime`

迁移后的关键变化：

| 关注点 | OpenAI Agents SDK 方案 | Pi Agent 方案 |
| --- | --- | --- |
| 运行边界 | Python FastAPI 独立运行时 | Next.js 通过 bridge 启动项目内 Pi 子进程 |
| 行为来源 | 系统提示词、Python 工具和 schema | 仓库技能文件，按需 `read` 相关 references |
| 部署 | Node + Python + 两套运行时 | Pi、扩展、技能、MCP 二进制随仓库交付 |
| 工具权限 | 业务工具注册和 guardrails | `--tools` 白名单、只读扩展、无写工具 |
| 事件与观测 | SDK 事件和 tracing | Pi JSONL 事件 + bridge 手工观测映射 |
| 模型/provider | 计划中以 OpenAI SDK 为中心 | 当前通过 Pi 配置 DeepSeek，也保留 provider/model 覆盖能力 |
| 主要代价 | 运行时和协议较完整，但跨服务复杂 | 交付简单，但 schema、trace、错误映射需要自己维护 |

迁移的决定性因素不是 API 风格，而是“哪个运行时已经成为真实主链路”。当 Pi 已经跑通技能加载、MCP 调用和 SSE 事件后，旧 Python runtime 已无调用方；继续保留它会让部署物里出现两套 Agent 行为来源。删除旧链路同时删除旧路由和测试，避免未来修 bug 时不知道改哪套实现。

依据：`docs/specs/09-17-pi-skill-runtime.md`、`lib/pi/bridge.ts`、`git show 73156bb`。

## 3. 不同选型背后的考量

### 3.1 为什么没有直接做固定 workflow

早期选择自主 ReAct，是为了验证 Agent 是否能根据用户诉求决定搜索、读取和推荐顺序；这符合当时 AI 工程实践中“先验证工具使用和任务完成，再固化流程”的思路。

但真实运行后发现，开放式循环会带来调用次数不可预测、同一笔记重复读取和失败重试放大的问题。因此当前更合理的方向不是完全回到脚本式流程，而是采用混合架构：阶段边界由代码约束，阶段内的证据判断和表达仍交给模型。

### 3.2 为什么技能文件成为行为来源

把研究方法、证据等级、两阶段推荐和输出格式放在 `SKILL.md` 与 references 中，有三个收益：

1. 规则可以像代码一样版本化、评审和测试，不必藏在 bridge 的长系统提示词里。
2. 通过渐进披露，只把技能描述常驻上下文，命中任务后再读取详细方法，减少初始上下文负担。
3. 运行时只守住通用约束；研究流程变更不需要改 bridge，降低“提示词副本”和真实规范漂移的风险。

这体现了开源 Agent 框架使用中常见的经验：模型能力不是唯一变量，工具描述、上下文装载方式、权限边界和可追溯规则同样决定稳定性。

### 3.3 为什么不把 MCP 原样暴露给模型

开源 MCP 的价值在于快速复用工具和数据连接，但它的工具集合通常按“服务能力”组织，而不是按“本产品允许的动作”组织。妆迹采用适配层和白名单，是在复用开源能力与控制副作用之间做的取舍：保留搜索资料的速度，隔离发布和账号操作风险。

### 3.4 为什么观测从自动 tracing 改为事件驱动

Pi 是独立子进程，OpenAI SDK 的同进程包装器无法完整看到 provider 请求。项目因此以 Pi JSONL 为唯一事实来源，在 bridge 边界记录墙钟耗时，再把事件映射为 Langfuse observation。这样牺牲了一些自动化，却能看到实际的 turn、模型调用、工具调用和淘宝卡片耗时。

这也是受 AI 工程实践影响后的一个重要修正：没有真实的调用链，就只能靠残差猜“模型慢还是工具慢”；先建立可观测性，再做性能优化。

## 4. AI 技术博客、业内经验和开源框架体验的影响

仓库目前没有保存具体博客 URL、文章标题或业内人士姓名，因此本文不把某个结论虚构归因给某位作者。能从项目决策和提交记录确认的影响，可以概括为以下几类工程共识：

1. **先做窄场景、再扩展 Agent 能力**：文本 MVP 先验证“妆效到产品”的核心价值，图片、长期记忆和交易后置。
2. **工具要小而有边界**：XHS 只读白名单、业务 adapter 不把 token 交给模型，避免“工具很多但权限不可控”。
3. **技能和提示词要版本化**：研究方法进入仓库文件，运行时只负责装载；这来自对开源 coding-agent/skill 体系的使用体验。
4. **模型不是全部，数据连接才是瓶颈**：真实 trace 证明主要耗时来自小红书浏览器/MCP，而不是模型推理。
5. **先可观测，再谈优化**：Langfuse 记录每一次模型和工具调用，修正了早期仅凭总耗时做残差归因的误判。
6. **框架应服从交付边界**：OpenAI Agents SDK 在能力上适合原型，但 Pi 在当前项目中更符合“Node 项目自包含、可替换 provider、技能与扩展同仓库”的交付目标。

如果需要在对外分享中明确引用博客或业内人士，应在本节补上真实来源链接，并把“受到启发”改写成“阅读/实践某来源后做出的具体决策”。目前仓库证据足以支持工程结论，但不足以支持具体署名。

## 5. 当前技术瓶颈

### 5.1 最大瓶颈是小红书 MCP，不是模型

2026-09-22 的真实链路数据：

- 第一轮总 trace 1369.5 秒，Pi 进程 1325.3 秒。
- 小红书调用 37 次，其中 25 次失败，失败率 68%；失败原因全部是 45 秒客户端超时。
- 失败调用合计墙钟 1494.1 秒；其中 7 次重试再次跑满，放大约 315 秒开销。
- 12 次成功的小红书调用仍然很慢：搜索平均 35.1 秒，详情平均 26.0 秒。
- 模型调用 21 次、合计 101.8 秒，占根 trace 约 7.4%，且没有失败。
- 第二轮仍是同一结论：小红书失败率 42%，模型约占 10% 以内。

因此当前不应优先通过“换更快模型”解决总延迟。先减少小红书调用、避免无效重试、修复浏览器/MCP 服务的稳定性，收益更大。

### 5.2 Agent 循环的调用数量不可预测

一轮中出现 21 次模型调用和 37 次 XHS 工具调用，说明开放式工具循环会把一次用户问题放大成很长的链路。详情读取失败后如果没有明确的失败记忆或预算控制，模型可能反复尝试；当前扩展已经对失败笔记做了本轮跳过，但还需要更上层的调用预算和阶段约束。

### 5.3 Pi 带来了自维护协议成本

Pi 的优点是轻量和可交付，但以下能力需要项目自己维护：

- 结构化答案校验和非法输出降级。
- JSONL 事件到 SSE、Langfuse 的稳定映射。
- 子进程退出、取消、超时和技能缺失的统一错误语义。
- provider/model 差异、token usage 和 cost 字段的兼容。

这不是迁移失败，而是把原来由 SDK 承担的成本转移到了项目代码。后续需要用契约测试把这部分固定下来。

### 5.4 证据链和内容体量会继续增长

当前真实搜索一次可以带回 20 条笔记和约 26KB 正文；Langfuse 记录脱敏全文有利于复盘，但会增加存储、隐私和摄取上限风险。后续需要区分“模型必须看到的上下文”和“供观测复盘的原文”，并对保留周期、开关和权限做产品化约束。

## 6. 预期解决路径

### P0：先把外部检索从长链路变成有预算的检索

1. 把搜索和详情设置不同超时；详情失败不再触发无条件重试。
2. 每轮限制搜索词数量、候选笔记数量和详情读取数量；同一 `feed_id` 去重。
3. 对已知不可读笔记做跨请求短 TTL 负缓存，避免每轮再次烧满超时窗口。
4. 为 XHS 增加熔断和健康状态：连续超时后快速返回 degraded，让模型基于已有证据结束。
5. 把“最低可用证据”写成终止条件，例如获得若干独立来源后停止继续翻页。

### P1：把自主 Agent 改成混合式 workflow

建议的阶段边界：

```text
澄清目标
  -> 生成少量检索词
  -> 搜索并挑选有限候选
  -> 读取有限详情
  -> 结构化妆容特征
  -> 映射产品能力与 SKU
  -> 校验答案并流式输出
```

代码控制阶段、预算和工具白名单；模型负责每个阶段里的语义判断。这样保留 Agent 的灵活性，同时让耗时和失败范围可预测。

### P1：增加结构化中间结果

让“妆容特征”“来源证据”“产品能力”“SKU 候选”分别有稳定 schema，最终回答再渲染成 Markdown。当前 `looktrace-products` 块已经证明“模型正文 + 机器可读块”可行，但下一步应补上版本化 JSON schema、校验失败修复和可观测的降级原因。

### P1：减少模型调用次数

通过一次计划调用生成检索计划，一次证据分析调用完成特征抽取，一次最终生成调用完成推荐；工具结果使用紧凑摘要，只有被选中的详情全文进入最终上下文。目标不是强行固定为三次，而是把“为什么继续调用”变成可解释的预算决策。

### P2：提升 MCP 服务本身的稳定性

需要把浏览器驱动当作独立基础设施治理：检查登录态、页面卡死、Chromium 生命周期、并发队列和服务重启；搜索与详情分开测量，避免用单一平均耗时掩盖不同故障。若上游长期不稳定，再评估缓存、异步采集或可替换的数据源，但不能用 mock 结果冒充实时资料。

### P2：建立运行时对比基准

保留 Pi 作为当前主链路，同时用同一组 eval case 比较 Pi、OpenAI Agents SDK、LangGraph/PydanticAI 等方案的：端到端延迟、工具调用次数、失败可解释性、结构化输出通过率、部署复杂度和观测完整度。只有在真实任务指标上出现持续差异，才值得再次更换运行时。

## 7. 评估这次迁移是否成功

迁移成功不应只看“能不能返回答案”，还应看：

- 部署是否自包含，是否不依赖全局 Pi、个人目录或临时目录。
- 技能规则是否只有一个来源，bridge 是否不再复制业务提示词。
- 写工具是否永远不可见，token/cookie 是否不进入模型、SSE 和 trace。
- 同一任务的模型调用、工具调用和失败原因是否能在 Langfuse 还原。
- 真实链路中，外部资料调用失败时是否能在预算内降级结束。
- 旧 Python runtime、旧路由和旧测试是否已删除，避免两套契约并存。

当前仓库已经满足前五项中的大部分工程基础，尚未解决的是外部小红书链路的稳定性、开放式循环的成本，以及 Pi 侧结构化协议的长期维护。

## 8. 小红书 V4 API 的替换评估

### 8.1 这份 API 能替换什么

用户提供的文档是 Just One API 的“小红书笔记搜索 API (V4)”：

```text
GET https://api.justoneapi.com/api/xiaohongshu/search-note/v4
```

它支持关键词、分页、排序、笔记类型和时间筛选，使用移动应用搜索流程。它可以直接替换当前链路中的“搜索发现”步骤，但文档没有定义 `data` 的具体 schema，也没有提供笔记详情、正文、评论或图片详情接口。

当前链路是：

```text
xhs_search_feeds -> 选择 feed_id/xsec_token -> xhs_get_feed_detail -> 模型分析
```

因此不能把 V4 搜索 API 直接描述成当前 MCP 的完整替代品。第一阶段最稳妥的架构是：

```text
V4 API 搜索 -> 取得候选笔记
                 |
                 └-> 仍由 MCP 读取少量详情 -> 模型分析
```

如果 V4 的实际返回体经验证包含可直接用于分析的正文、标签、图片和作者信息，才可以进一步减少详情 MCP 调用；目前 OpenAPI 只把 `data` 声明为任意对象，不能据文档做这个假设。

### 8.2 现有耗时的准确归因

2026-09-22 的真实 trace 不能简单把所有调用时长相加，因为模型、工具和不同 turn 可能重叠。应同时看“根 trace 墙钟”和“调用累计时长”：

| 模块 | 真实数据 | 相对根 trace 的解释 | 判断 |
| --- | --- | --- | --- |
| 模型调用 | 第一轮 21 次、101.8 秒；根 trace 1369.5 秒，约 7.4% | 模型没有失败，平均 4.8 秒 | 不是当前首要瓶颈 |
| XHS 失败调用 | 25/37 次失败，失败累计 1494.1 秒，100% 为 45 秒客户端超时 | 失败率 68%，且重试有 7 次再次跑满约 90 秒 | 最大短板 |
| XHS 成功调用 | 12 次、累计 318 秒；搜索平均 35.1 秒，详情平均 26.0 秒 | 成功调用也明显偏慢 | 外部浏览器/MCP 瓶颈 |
| 淘宝卡片 | 8 张卡片约 81.9 秒，发生在 Pi 进程之后 | 影响完整答案到达时间，不影响答案正文先出 | 次要瓶颈 |
| 进程/JSON 管道/turn 间隙 | 残差约 10 秒 | 相比 XHS 很小 | 暂不优先优化 |

第二轮根 trace 为 960.5 秒，XHS 失败率仍为 42%，模型调用为 96.9 秒且没有失败。两轮共同指向同一个结论：先优化 XHS 数据链路，比先换模型更有收益。

### 8.3 只替换搜索时，能省多少

两轮真实 trace 都大约执行了 5 次搜索调用。当前搜索调用成功时平均约 35.1–46.0 秒，失败则通常耗满 45 秒；V4 API 文档只给出建议超时 60–120 秒，没有 SLA，因此必须先压测，不能直接承诺具体延迟。

可用下面的公式做容量估算：

```text
搜索阶段理论节省 ≈ 搜索次数 × (当前搜索平均耗时 - V4 API 平均耗时)
                 ≈ 5 × (35–46 - V4 平均耗时) 秒
```

如果压测得到 V4 平均 2–5 秒，搜索阶段大约可节省 150–220 秒，即 2.5–3.7 分钟。把这个节省近似映射到根 trace，第一轮 1369.5 秒可能降到约 1150–1220 秒，第二轮 960.5 秒可能降到约 740–810 秒。这里是“搜索替换的估算区间”，不是线上 SLA，因为详情 MCP 仍可能占据主路径，且调用有重叠。

如果 V4 平均 10 秒，预计节省约 125–180 秒；如果 V4 也需要 30 秒以上，收益会明显变小，只剩统一搜索入口、分页和筛选能力的产品收益。

### 8.4 如果未来详情也能通过 API 替换

这是潜在的上限收益，但当前文档没有提供详情 API，不能作为已确认结论。第一轮有 31 次详情调用，第二轮有 27 次；详情成功均值在两轮分别为 26.0 秒和 41.5 秒，失败还会额外烧超时窗口。

若未来存在稳定的详情接口，并且能提供正文、标签、图片/视频信息和必要的作者元数据，那么可以：

1. 由代码从搜索结果中选固定数量的候选，例如 4–8 篇。
2. 并发调用详情 API，设置独立预算。
3. 达到最低证据数量后停止继续读取。
4. 只把选中的详情送入模型。

相比当前 27–31 次详情读取，减少到 4–8 次本身就可能节省数百秒；如果详情 API 是普通 HTTPS 且平均几秒，整轮有机会从 16 分钟级降到 3–6 分钟级。但这依赖三个未验证前提：详情接口确实存在、返回字段足够、API 的限流和成功率稳定。现在不能把这个范围当成承诺。

### 8.5 推荐的迁移方案

建议分三步做，而不是直接替换生产链路：

**第一步：影子压测。** 对同一组关键词，同时记录现有 MCP 搜索和 V4 搜索的首字节时间、完整响应时间、返回条数、重复率、结果相关性和错误码；不把 V4 结果直接展示给用户。

**第二步：搜索层替换。** 新增服务端 `xhsSearchProvider` 适配器，保留统一业务返回结构。V4 token 只从服务端环境变量读取，不能拼进日志、trace、模型上下文或客户端；按业务 `code` 处理成功、采集失败、限流、配额、鉴权和余额错误。

**第三步：减少详情读取。** 不让模型无限枚举详情。代码侧按排序和去重结果选择 4–8 篇，详情仍走 MCP；如果后续确认有可用详情 API，再替换详情 provider。

重试策略应按错误码区分：`301` 采集失败最多一次受控重试；`302/303/601/602` 不重试并快速降级；`100/600` 直接报告配置或权限错误；网络超时使用短预算，不能照搬文档的 120 秒作为每次 Agent 调用超时。V4 文档建议 60–120 秒是单接口容忍时间，不等于整轮 Agent 应该等待 120 秒。

### 8.6 迁移后的预期短板

切换 V4 后，XHS 搜索的浏览器启动和页面交互成本预计会下降，但会新增几类风险：API 供应商限流和配额、token 余额、返回 schema 不稳定、搜索结果和 MCP 详情之间的 ID/链接关联，以及 API 结果是否包含足够的视觉证据。最终推荐仍需要真实 trace 对比以下指标：

- `xhs.search` p50/p95、错误率和重试率。
- `xhs.detail` p50/p95、可读率和每轮调用数量。
- 每轮模型调用次数与输入上下文字节数。
- 最低证据数量达成率和最终答案质量。
- 根 trace 墙钟、答案正文可用时间、完整卡片可用时间。

只有当 V4 在这些指标上稳定优于 MCP，才应把它设为默认 provider；否则保留 provider 开关，在 API 失败时以明确 degraded 状态结束，而不是静默伪造或回退到 mock。
